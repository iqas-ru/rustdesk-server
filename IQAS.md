# iQAS: режим доступа по личным ключам сотрудников

Ветка `iqas-access` поверх rustdesk-server 1.1.17. Клиенты — стоковый RustDesk 1.5.0.

## Что делает патч

Режим включается только переменной `ACCESS_KEYS_FILE` (env или `.env`). Если она не задана, сервер
работает как upstream.

- **hbbs**: запрос на подключение (`PunchHoleRequest`) принимается только с личным ключом активного
  сотрудника. Общий ключ сервера для инициации **не принимается** (клиент получит "Key mismatch").
  В лог пишется строка `AUDIT <имя> <адрес> -> <ID>`.
- **hbbs**: подпись `IdPk` (по ней клиент проверяет подлинность удаленной стороны) делается секретным
  ключом того сотрудника, который запросил соединение. Если сотрудника нет или он отозван, ответ не
  отправляется вовсе: клиент никогда не получит пустую подпись и не перейдет на незащищенное соединение.
- **hbbs**: `RequestRelay` пересылается только после свежего (≤120 с) разрешенного запроса с того же
  IP к тому же ID; лишние поля (права, контекст, токен, switch_code) отбрасываются.
- **hbbr**: принимается общий ключ (сторона клиента, `id` пустой) или личный ключ сотрудника.
  Пара соединяется, только если ровно одна сторона управляющая и у нее активный личный ключ.
  При отзыве ключа сессия через relay рвется (проверка каждые ~3 с).

## Файл ключей

```
# имя<TAB>секретный ключ (base64, 64 байта libsodium)
Ivanov	<secret key base64>
Petrov	<secret key base64>
```

Пустые строки и `#` игнорируются, битые строки пропускаются с предупреждением в логе. Публичный ключ =
base64 последних 32 байт секретного; его сотрудник вписывает в поле **Key** своего клиента.
Генерация пары:

```
docker run --rm --entrypoint /usr/bin/rustdesk-utils ghcr.io/<owner>/rustdesk-server-iqas genkeypair
```

Файл перечитывается каждые 5 с. Права 600, один и тот же файл монтируется в hbbs и hbbr, например
`ACCESS_KEYS_FILE=/root/access_keys.tsv`. Клиенты заказчиков остаются на общем ключе (`-k _`).

Личный публичный ключ фактически служит пропуском: не публиковать, при утечке — отзывать.

## Fail-closed

Файл не задан → обычный режим. Файл задан, но отсутствует, не читается или пуст → не пускается никто
(ошибка в логе). Сервер при этом работает, после исправления файла доступ восстанавливается за ≤5 с.

## Отзыв

Удалить строку сотрудника из файла.

- Новые подключения отклоняются сразу после перечитывания (≤5 с).
- Живые сессии через relay обрываются (≤5 с + ~3 с).
- Живые прямые P2P-сессии продолжаются до их завершения: сервер в них не участвует. Если нужен
  жесткий отзыв, на hbbs ставится `ALWAYS_USE_RELAY=Y`: тогда сессии идут через relay и рвутся
  при отзыве (исключение upstream: обе стороны за одним внешним IP соединяются напрямую по LAN).

## Матрица проверки

| # | Сценарий | Ожидается |
|---|----------|-----------|
| 1 | `ACCESS_KEYS_FILE` не задан, клиент с общим ключом | работает как upstream |
| 2 | Сотрудник (личный ключ) → ПК заказчика, напрямую | подключение, значок шифрования, `AUDIT` в логе hbbs |
| 3 | То же через relay (`ALWAYS_USE_RELAY=Y` или «Force relay» в клиенте) | подключение через hbbr, шифрование |
| 4 | То же в одной локальной сети | подключение (путь LocalAddr) |
| 5 | Клиент с общим ключом → любой ID | "Key mismatch" |
| 6 | Клиент с неизвестным ключом | "Key mismatch" |
| 7 | Сотрудник → ПК другого сотрудника | подключение |
| 8 | Удалить строку сотрудника | через ≤5 с новые подключения "Key mismatch"; relay-сессия рвется; P2P живет до конца |
| 9 | Удалить/испортить файл | не пускается никто, ошибка в логе; вернуть файл → доступ за ≤5 с |
| 10 | Битая строка в файле | пропущена с предупреждением, остальные работают |
